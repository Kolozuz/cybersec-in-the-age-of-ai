# Capítulo 4 — Software

> **Cada programa que ejecutas es una decisión de confianza.**

Nuestro computador puede parecer una herramienta pasiva:

```text
Abrir navegador
Abrir documento
Instalar aplicación
Ejecutar script
```

Pero cada programa que ejecutamos obtiene determinadas capacidades sobre el sistema.

Puede:

* leer archivos;
* escribir información;
* acceder a la red;
* utilizar dispositivos;
* acceder a credenciales;
* interactuar con otros programas;
* procesar información sensible.

Por eso una pregunta sencilla resulta fundamental:

> **¿Qué estoy ejecutando y por qué debería confiar en ello?**

---

# 1. Concepto

## Software es superficie de ataque

Podemos representar un dispositivo de esta manera:

```text
                  DISPOSITIVO
                      │
        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
    Navegador    Aplicaciones     Sistema
        ↓             ↓             ↓
    Extensiones    Plugins       Drivers
        └─────────────┼─────────────┘
                      ↓
                    Datos
```

Cada componente añade funcionalidad.

Y, potencialmente:

> **una nueva superficie de ataque.**

Esto no significa que debamos desconfiar de todo software.

Significa que debemos entender que **instalar software es otorgarle capacidades**.

---

## El ciclo de vida del software

Una forma útil de pensar el problema es:

```text
Descubrir
   ↓
Descargar
   ↓
Instalar
   ↓
Ejecutar
   ↓
Actualizar
   ↓
Mantener
   ↓
Eliminar
```

Cada etapa plantea preguntas de seguridad.

### Descubrir

¿Dónde encontré el programa?

### Descargar

¿Estoy obteniéndolo de una fuente legítima?

### Instalar

¿Qué permisos solicita?

### Ejecutar

¿Qué puede hacer?

### Actualizar

¿Estoy recibiendo correcciones de seguridad?

### Mantener

¿Sigo necesitando este software?

### Eliminar

¿Se eliminó realmente y dejó de tener acceso?

---

# Software confiable ≠ software seguro

Esta distinción es importante.

Podemos descargar una aplicación desde su sitio oficial y aun así encontrarnos con:

* una vulnerabilidad;
* una configuración insegura;
* una dependencia vulnerable;
* un componente comprometido;
* un bug.

Por tanto, hay dos preguntas diferentes:

> **¿Es auténtico el software?**

y

> **¿Es seguro utilizarlo?**

La primera trata principalmente sobre **origen e integridad**.

La segunda sobre **riesgo**.

---

# Vulnerabilidad, exploit y compromiso

Estos conceptos aparecen constantemente en ciberseguridad y conviene diferenciarlos.

### Vulnerabilidad

Una debilidad que puede ser utilizada para provocar un comportamiento no deseado.

### Exploit

Una técnica o código que aprovecha una vulnerabilidad.

### Compromiso

La consecuencia: el atacante consigue algún grado de acceso, ejecución, extracción de información u otra capacidad no autorizada.

Podemos visualizarlo:

```text
Debilidad
    ↓
Vulnerabilidad
    ↓
Exploit
    ↓
Compromiso
    ↓
Impacto
```

Una vulnerabilidad no implica automáticamente que nuestro sistema haya sido comprometido.

Pero sí significa:

> **Existe una condición que debemos evaluar y, cuando corresponda, corregir.**

---

# CVE y CWE

Para el público técnico conviene introducir dos conceptos que aparecerán repetidamente.

## CVE

**CVE (Common Vulnerabilities and Exposures)** identifica vulnerabilidades conocidas de productos y componentes.

Conceptualmente:

```text
CVE
 ↓
"Existe esta vulnerabilidad conocida"
 ↓
Producto / versión afectada
 ↓
¿Estoy expuesto?
```

## CWE

**CWE (Common Weakness Enumeration)** describe tipos de debilidades que pueden conducir a vulnerabilidades.

Por ejemplo:

```text
CWE
 ↓
Tipo de debilidad
 ↓
Código / diseño
 ↓
Vulnerabilidad
```

MITRE mantiene CWE como una clasificación de debilidades de software y hardware que pueden convertirse en vulnerabilidades. ([CWE][1])

La distinción simplificada:

> **CWE describe la debilidad; CVE identifica una vulnerabilidad concreta.**

---

# 2. Amenaza

## Malware

**Malware** es software diseñado para realizar acciones maliciosas.

Puede tener objetivos muy diferentes:

* robar información;
* obtener credenciales;
* espiar;
* cifrar archivos;
* instalar otros componentes;
* controlar un dispositivo;
* participar en una botnet.

No todo malware se comporta igual.

---

## Infostealers

Un **infostealer** busca principalmente información que pueda ser reutilizada por un atacante.

Puede intentar obtener:

* credenciales;
* cookies;
* tokens;
* información almacenada en navegadores;
* datos de aplicaciones;
* información del sistema.

Esto conecta directamente con nuestros capítulos anteriores:

```text
Infostealer
    ↓
Credenciales
    ↓
Identidad
    ↓
Acceso
    ↓
Datos
```

Es un buen ejemplo de por qué los capítulos de la guía no son problemas aislados.

---

# Ransomware

El ransomware busca impedir el acceso a información o sistemas, normalmente mediante cifrado, para posteriormente exigir algún tipo de pago o acción.

Conceptualmente:

```text
Sistema
  ↓
Ransomware
  ↓
Archivos inaccesibles
  ↓
Impacto
```

Aquí aparece una distinción importante:

> **La prevención no es suficiente.**

Si los controles preventivos fallan, necesitamos:

```text
Backup
   ↓
Recovery
   ↓
Continuidad
```

Esto nos llevará con más profundidad al **Capítulo 6 — Resiliencia y respuesta**.

---

# Software pirata y cracks

Uno de los riesgos más fáciles de entender:

```text
Software comercial
       ↓
"No quiero pagar"
       ↓
Crack / keygen / versión modificada
       ↓
Código desconocido
       ↓
¿Quién lo modificó?
```

El problema no es solamente legal.

Al instalar una versión modificada estamos aceptando software cuyo origen e integridad son mucho más difíciles de verificar.

Además, los cracks y keygens constituyen un mecanismo atractivo para distribuir malware porque el usuario está dispuesto a desactivar controles o aceptar advertencias con tal de ejecutar el programa.

La regla práctica:

> **Si el software fue modificado para eliminar controles de seguridad, no debemos asumir que el único cambio fue eliminar el control que nos molestaba.**

---

# Fake installers

No necesitamos descargar software pirata para caer en una descarga maliciosa.

Un atacante puede crear una página que imite la distribución de una aplicación legítima.

```text
Buscador
   ↓
"Descargar aplicación X"
   ↓
Sitio falso
   ↓
Instalador falso
   ↓
Malware
```

La interfaz puede ser completamente convincente.

Por eso:

> **La apariencia de legitimidad no es evidencia suficiente de legitimidad.**

---

# Malvertising

La publicidad también puede formar parte de la cadena de ataque.

Por ejemplo:

```text
Usuario busca aplicación
        ↓
Resultado / anuncio
        ↓
Sitio controlado por atacante
        ↓
Descarga
```

Esto es particularmente peligroso porque el usuario puede estar intentando hacer exactamente lo correcto:

> "Voy a buscar el sitio oficial."

El problema es **qué resultado decidió utilizar**.

---

# Extensiones del navegador

Una extensión puede parecer una pequeña funcionalidad:

* bloqueador de anuncios;
* gestor de contraseñas;
* traductor;
* herramienta de productividad;
* integración con IA.

Pero una extensión puede solicitar permisos importantes.

Por ejemplo:

```text
"Leer y modificar datos
en todos los sitios web"
```

Eso no significa automáticamente que sea maliciosa.

Pero sí significa:

> **Estamos otorgándole una capacidad considerable.**

Por eso las extensiones deberían recibir el mismo nivel de escrutinio que cualquier otro software.

---

# Dependencias

Para un desarrollador, existe otro problema menos visible.

Una aplicación rara vez está compuesta únicamente por código propio:

```text
Aplicación
   │
   ├── Framework
   ├── Library A
   ├── Library B
   ├── Library C
   │       └── Dependency X
   │              └── Dependency Y
   └── Build tools
```

Es una **cadena de suministro de software**.

OWASP señala que las aplicaciones modernas dependen de numerosos componentes, incluyendo librerías de terceros, gestores de paquetes, herramientas de build, sistemas de control de versiones y CI/CD; una vulnerabilidad en un único componente puede afectar a toda la cadena. ([OWASP Cheat Sheet Series][2])

---

# Supply chain attack

Esto introduce una amenaza diferente.

En lugar de atacar directamente:

```text
Nuestra aplicación
```

el atacante puede intentar comprometer:

```text
Proveedor
   ↓
Dependencia
   ↓
Nuestra aplicación
   ↓
Nuestros usuarios
```

El ataque se mueve hacia una parte de la cadena que confiamos.

Esto es importante porque:

> **No sólo debemos proteger aquello que construimos; también debemos entender aquello de lo que dependemos.**

---

# 3. Ejemplo — "Sólo necesitaba una herramienta"

Imaginemos que necesitamos convertir un archivo.

Buscamos:

```text
"PDF converter free"
```

Encontramos una página convincente.

Descargamos:

```text
PDFConverterSetup.exe
```

Lo instalamos.

La aplicación aparentemente funciona.

Pero en segundo plano también se instaló un componente que roba información del navegador.

El usuario podría no notar nada.

```text
Usuario
  ↓
"Convertir PDF"
  ↓
Software aparentemente legítimo
  ↓
Infostealer
  ↓
Cookies / credenciales
  ↓
Atacante
```

Lo interesante del ejemplo es que **ningún paso requirió que el usuario tuviera una conducta evidentemente irresponsable**.

El usuario simplemente:

1. necesitaba una herramienta;
2. buscó una solución;
3. descargó un programa;
4. lo ejecutó.

El fallo estuvo en la **cadena de confianza**.

# 4. Control

La defensa empieza antes de instalar.

## 1. Fuente

Preferir:

```text
Proveedor oficial
        ↓
Repositorio oficial
        ↓
App Store / package registry confiable
```

sobre:

```text
Mirror desconocido
Crack
Torrent
Link aleatorio
Adjunto inesperado
```

La fuente no garantiza seguridad, pero reduce incertidumbre.

---

## 2. Necesidad

Preguntarnos:

> **¿Realmente necesito este software?**

Cada aplicación innecesaria:

```text
+ software
+ permisos
+ actualizaciones
+ dependencias
+ superficie de ataque
```

Eliminar software que ya no utilizamos es una medida de reducción de superficie.

---

# 3. Actualizaciones

Una actualización puede incluir:

* nuevas funcionalidades;
* correcciones de bugs;
* mejoras de rendimiento;
* **parches de seguridad**.

Por eso:

> **"Funciona" no significa "está actualizado".**

Una vulnerabilidad puede existir durante meses sin que el usuario note ningún problema.

NIST recomienda incorporar prácticas de desarrollo y mantenimiento que permitan reducir vulnerabilidades y mitigar el impacto de aquellas que no hayan sido detectadas o corregidas. ([NIST CSRC][3])

---

# 4. Permisos

Cuando una aplicación solicita:

```text
Camera
Microphone
Location
Contacts
Files
Network
```

deberíamos preguntarnos:

> **¿Necesita realmente este permiso para hacer aquello que quiero?**

El principio general es **least privilege**:

> Conceder únicamente las capacidades necesarias para realizar una tarea.

Esto aplica tanto a usuarios como a aplicaciones.

---

# 5. Antivirus y EDR

Estas herramientas ayudan a detectar comportamientos o artefactos asociados con software malicioso.

La diferencia conceptual:

### Antivirus

Tradicionalmente asociado con detección y prevención de malware.

### EDR

**Endpoint Detection and Response** amplía la visibilidad hacia:

* eventos;
* procesos;
* comportamiento;
* conexiones;
* investigación;
* respuesta.

No necesitamos entrar todavía en su arquitectura.

El takeaway:

> **La seguridad del endpoint no depende de que el usuario reconozca personalmente todo el malware.**

---

# 6. Sandboxing

Un sandbox intenta limitar lo que un programa puede hacer.

Conceptualmente:

```text
           Sistema
              │
       ┌──────┴──────┐
       │   Sandbox   │
       │             │
       │ Aplicación  │
       │             │
       └─────────────┘
```

Si la aplicación se comporta mal, el objetivo es que su capacidad para afectar al resto del sistema sea limitada.

Esto sigue el mismo principio que veremos repetidamente:

> **Reducir el impacto de un compromiso.**

---

# 7. Software supply chain

Para equipos técnicos:

### Inventariar dependencias

Saber:

```text
¿Qué componentes utilizamos?
¿Qué versiones?
¿De dónde vienen?
```

### Monitorizar vulnerabilidades

```text
Dependency
   ↓
Known vulnerability
   ↓
¿Nuestra versión está afectada?
   ↓
Update / mitigate
```

### SBOM

Un **Software Bill of Materials (SBOM)** permite describir los componentes que forman parte de un producto de software.

No es una solución de seguridad por sí misma.

Es visibilidad.

Y:

> **No podemos gestionar una dependencia que ni siquiera sabemos que tenemos.**

OWASP recomienda mantener visibilidad de las dependencias y automatizar su inventario y monitorización de vulnerabilidades; SBOM puede ayudar a ello. ([OWASP Cheat Sheet Series][2])

# 5. El lente de la IA

Aquí la IA encaja especialmente bien con nuestra convención de cuatro categorías:

```text
IA
├── Amplificador
├── Nueva superficie
├── Nueva herramienta
└── Cambio de threat model
```

---

## IA como amplificador

La IA puede ayudar a generar o modificar código mucho más rápidamente.

Eso tiene una consecuencia doble:

```text
IA
 ↓
Más código
 ↓
Más rápido
 ↓
Más capacidades
```

pero también:

```text
IA
 ↓
Más código
 ↓
Más rápido
 ↓
Más posibilidades de introducir errores
```

La velocidad de producción no equivale a velocidad de validación.

---

# Código generado por IA

Supongamos:

```text
Developer
    ↓
"Genera una implementación para X"
    ↓
LLM
    ↓
Código
    ↓
"Funciona"
```

La pregunta de seguridad debería ser:

```text
¿Funciona?
     +
¿Es correcto?
     +
¿Es seguro?
```

Una IA puede generar código:

* vulnerable;
* innecesariamente complejo;
* con dependencias innecesarias;
* con APIs inexistentes;
* con configuraciones inseguras;
* con secrets introducidos accidentalmente.

Por eso:

> **El código generado por IA sigue siendo código que debemos revisar.**

NIST ya ha desarrollado un perfil específico del SSDF para prácticas relacionadas con el desarrollo de IA generativa y modelos fundacionales, precisamente como extensión de las prácticas de desarrollo seguro. ([NIST CSRC][4])

---

# IA como nueva herramienta para atacantes

Un atacante también puede utilizar IA para acelerar:

* generación de código malicioso;
* análisis de software;
* búsqueda de información;
* automatización;
* adaptación de malware;
* creación de aplicaciones falsas.

El principio no necesariamente es nuevo.

Lo que cambia es:

> **la barrera de entrada y la velocidad de iteración.**

Esto es coherente con la categoría **amplificador**, que utilizamos como convención para la guía. 

---

# Paquetes maliciosos y IA

Los ecosistemas de paquetes ya constituyen una superficie de supply chain.

Ahora imaginemos que utilizamos IA para generar código:

```text
Prompt
  ↓
"Necesito una librería para X"
  ↓
AI
  ↓
Dependency
  ↓
npm / PyPI / etc.
```

Podemos terminar incorporando:

* una dependencia innecesaria;
* una dependencia abandonada;
* una dependencia vulnerable;
* un paquete malicioso.

El problema no es que la IA "quiera" hacer algo malicioso.

Es que:

> **Un modelo puede recomendar una dependencia sin que esa recomendación constituya una validación de seguridad.**

---

# AI-generated applications

La barrera para crear software también está bajando.

Una persona puede pasar de:

```text
"No sé programar"
```

a:

```text
"Construí esta aplicación"
```

en mucho menos tiempo.

Eso es extraordinariamente útil.

Pero también significa que habrá más software:

```text
Más software
   ↓
Más aplicaciones
   ↓
Más código
   ↓
Más componentes
   ↓
Más superficie de ataque
```

Por tanto, el crecimiento de software generado por IA también debe venir acompañado de:

* revisión;
* testing;
* análisis de dependencias;
* gestión de secrets;
* actualización;
* controles de acceso.

---

# IA como herramienta defensiva

La misma tecnología puede utilizarse para defender.

Por ejemplo:

```text
Código
  ↓
IA
  ↓
"Encuentra posibles problemas"
  ↓
Developer
  ↓
Validación
```

También puede ayudar con:

* code review;
* análisis de vulnerabilidades;
* explicación de CVEs;
* actualización de dependencias;
* análisis de logs;
* investigación de malware.

Pero debemos mantener una regla:

> **IA puede ayudar a encontrar problemas; no debería ser la única autoridad para decidir que no existen.**

---

# Una nueva pregunta de confianza

Antes:

> "¿Puedo confiar en este software?"

Ahora debemos añadir:

> **"¿Cuánto de este software fue generado, seleccionado o modificado por IA y cómo fue validado?"**

No porque el código generado por IA sea inherentemente inseguro.

Sino porque:

> **la procedencia y el proceso de validación también forman parte del modelo de confianza.**

---

# 6. Takeaways

> ## **Instalar software es otorgarle capacidades a alguien que no conocemos personalmente.**

1. **El software es una superficie de ataque porque puede acceder a recursos, datos y redes del dispositivo.**

2. **La fuente importa: autenticidad, integridad y seguridad son preguntas distintas.**

3. **Mantener software actualizado reduce el riesgo de vulnerabilidades conocidas, pero actualizar no sustituye otros controles.**

4. **Extensiones, plugins y dependencias también son software y deben formar parte de nuestro modelo de confianza.**

5. **Las dependencias convierten nuestras aplicaciones en cadenas de suministro: no podemos proteger aquello que no sabemos que utilizamos.**

6. **La IA acelera la creación de software, pero no garantiza que el resultado sea correcto o seguro.**

7. **Código generado por IA debe revisarse como cualquier otro código.**

8. **La IA también puede convertirse en una herramienta defensiva para analizar código, vulnerabilidades y dependencias.**
